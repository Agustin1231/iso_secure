Metodologia STRIDE

El modelo STRIDE fue desarrollado por Microsoft como un marco sistematico para identificar amenazas de seguridad en sistemas de software. Cada letra representa una categoria de amenaza que viola una propiedad de seguridad especifica.

S
Spoofing
Suplantacion de identidad
Viola: Autenticacion
T
Tampering
Manipulacion de datos
Viola: Integridad
R
Repudiation
Negacion de acciones
Viola: No repudio
I
Info Disclosure
Divulgacion de informacion
Viola: Confidencialidad
D
Denial of Service
Denegacion de servicio
Viola: Disponibilidad
E
Elev. of Privilege
Escalamiento de privilegios
Viola: Autorizacion

El proceso de modelamiento de amenazas de Microsoft sigue cuatro pasos fundamentales: (1) Diagramar el sistema e identificar los flujos de datos, (2) Identificar los limites de confianza donde los datos cruzan entre zonas de diferente nivel de privilegio, (3) Aplicar el modelo STRIDE a cada componente y flujo de datos para enumerar amenazas potenciales, y (4) Definir mitigaciones para cada amenaza identificada.

Para ISO SECURE, este analisis es especialmente critico dado que el sistema maneja datos sensibles de cumplimiento ISO 27001, incluyendo evaluaciones de riesgo, incidentes de seguridad, informacion de auditorias internas y datos de multiples organizaciones bajo un modelo multi-tenant.

Limites de confianza identificados: Se identifican 4 limites de confianza principales en el sistema. El primer limite separa la zona no confiable (Internet/usuarios) del contenedor Docker. El segundo limite aisla la red Docker interna (bridge network) donde residen los contenedores de frontend y backend. El tercer limite protege la capa de aplicacion backend donde se ejecuta la logica de negocio, la validacion JWT y el control de acceso RBAC. El cuarto limite corresponde a los servicios externos gestionados por Supabase (base de datos PostgreSQL y servicio de autenticacion).

Los flujos de datos criticos que cruzan estos limites incluyen: (1) credenciales de usuario en el login, (2) tokens JWT en cada request API, (3) datos de incidentes/riesgos/controles en operaciones CRUD, (4) queries SQL hacia la base de datos con datos multi-tenant, y (5) validaciones de token contra el servicio Auth de Supabase.

04

Analisis STRIDE por Componente

Aplicacion sistematica del modelo STRIDE a cada componente y flujo de datos del sistema.

S  SPOOFING — Suplantacion de Identidad
Amenazas de Suplantacion
Propiedad violada: Autenticacion — Un atacante se hace pasar por un usuario o componente legitimo
  • S-01
    Robo de JWT y reutilizacion de sesion
    Un atacante intercepta o roba un token JWT valido (via XSS, red no cifrada o malware) y lo reutiliza para autenticarse como el usuario victima. Los tokens JWT son stateless, por lo que el backend no puede invalidarlos una vez emitidos.
    CRITICO
  • S-02
    Suplantacion de Supabase Auth Service
    Un atacante realiza un ataque Man-in-the-Middle entre el backend y el servicio Supabase Auth (/auth/v1/user), respondiendo con un usuario falso validado. Esto permitiria autenticacion fraudulenta.
    ALTO
  • S-03
    Registro de usuario con email corporativo falso
    Un atacante se registra con un email que no le pertenece para ganar acceso al sistema. Al no existir verificacion de dominio corporativo, podria registrarse con emails genericos y solicitar asignacion a una empresa.
    ALTO
  • S-04
    Falsificacion de origen en CORS abierto
    La configuracion CORS actual permite todos los origenes (allow_origins=["*"]), lo que permite a cualquier dominio malicioso realizar peticiones autenticadas al API si el usuario tiene una sesion activa.
    CRITICO
T  TAMPERING — Manipulacion de Datos
Amenazas de Manipulacion
Propiedad violada: Integridad — Modificacion no autorizada de datos en transito o en reposo
  • T-01
    Manipulacion de datos de cumplimiento ISO
    Un usuario con rol de analista podria manipular el porcentaje de cumplimiento (compliance_pct) de los controles ISO asignados a su empresa, reportando valores artificialmente altos para aparentar un nivel de cumplimiento mayor al real.
    ALTO
  • T-02
    Inyeccion SQL via parametros de query
    Aunque SQLAlchemy proporciona proteccion contra inyeccion SQL mediante consultas parametrizadas, si existiera alguna query construida con concatenacion directa de strings, un atacante podria inyectar SQL malicioso para modificar o extraer datos.
    MEDIO
  • T-03
    Alteracion de severidad de incidentes
    Un usuario autorizado podria cambiar la severidad de incidentes criticos a niveles bajos para ocultar problemas graves de seguridad, afectando los KPIs del dashboard y la toma de decisiones de la alta direccion.
    ALTO
  • T-04
    Manipulacion de empresa_id en requests
    Un atacante podria intentar enviar un empresa_id diferente al propio en las peticiones API para crear, modificar o eliminar datos pertenecientes a otra organizacion, violando el aislamiento multi-tenant.
    CRITICO
R  REPUDIATION — Negacion de Acciones
Amenazas de Repudio
Propiedad violada: No repudio — Un actor niega haber realizado una accion sin posibilidad de demostrar lo contrario
  • R-01
    Ausencia de logs de auditoria de acciones
    El sistema no cuenta con un sistema de logging de acciones de usuario (audit trail). Un administrador podria modificar roles, eliminar datos o alterar evaluaciones de riesgo sin dejar rastro auditable, imposibilitando la trazabilidad.
    CRITICO
  • R-02
    Negacion de creacion/modificacion de incidentes
    Sin registros de quien creo o modifico un incidente (mas alla de reported_by que es un campo de texto libre), un usuario podria negar haber reportado un incidente critico o haber cambiado su estado de abierto a cerrado prematuramente.
    ALTO
  • R-03
    Manipulacion de snapshots historicos sin trazabilidad
    Los KPI snapshots registran metricas historicas, pero no hay registro de quien los creo ni si fueron modificados posteriormente. Un actor podria alterar datos historicos para falsificar tendencias de mejora.
    ALTO
I  INFORMATION DISCLOSURE — Divulgacion de Informacion
Amenazas de Divulgacion
Propiedad violada: Confidencialidad — Exposicion de informacion a entidades no autorizadas
  • I-01
    Fuga de datos multi-tenant entre empresas
    Si el filtro _empresa_filter() falla o no se aplica correctamente en algun endpoint, un usuario de la Empresa A podria acceder a datos de incidentes, controles o riesgos de la Empresa B, violando el aislamiento de datos.
    CRITICO
  • I-02
    Exposicion de datos sensibles en respuestas API
    Los endpoints de /dashboard/export y /dashboard/summary consolidan KPIs de todo el sistema. Si un usuario con permisos limitados accede a estos endpoints sin filtrado adecuado, podria obtener informacion agregada de todas las organizaciones.
    ALTO
  • I-03
    Documentacion Swagger expuesta en produccion
    Los endpoints /docs (Swagger) y /redoc estan habilitados sin restriccion. En produccion, esto expone la estructura completa del API, schemas de datos, parametros y respuestas a cualquier atacante, facilitando el reconocimiento.
    MEDIO
  • I-04
    Exposicion de credenciales en variables de entorno
    Las claves de Supabase (SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY) y el DATABASE_URL se almacenan en variables de entorno. Si el contenedor Docker es comprometido o los archivos .env se exponen, todas las credenciales quedan al descubierto.
    ALTO
  • I-05
    Informacion de empresas (NIT, contacto) sin cifrado
    Datos sensibles como el NIT, representante legal, telefono y email de las empresas se almacenan en texto plano en la base de datos. Una brecha en la base de datos expondria directamente esta informacion.
    ALTO
D  DENIAL OF SERVICE — Denegacion de Servicio
Amenazas de Disponibilidad
Propiedad violada: Disponibilidad — El sistema se vuelve inaccesible para usuarios legitimos
  • D-01
    Ausencia de rate limiting en endpoints API
    No existe limitacion de tasa de peticiones (rate limiting) en ningun endpoint. Un atacante podria enviar miles de peticiones por segundo a endpoints costosos como /dashboard/summary (que ejecuta multiples queries agregadas) saturando el backend y la base de datos.
    CRITICO
  • D-02
    Agotamiento de conexiones de base de datos
    Sin un pool de conexiones correctamente limitado, un ataque de fuerza bruta o multiples sesiones simultaneas podrian agotar las conexiones disponibles de asyncpg al PostgreSQL de Supabase, dejando al sistema sin acceso a datos.
    ALTO
  • D-03
    Ataque de fuerza bruta al login
    Sin limite de intentos fallidos de login, un atacante podria ejecutar ataques de fuerza bruta contra cuentas de usuario, generando carga excesiva en Supabase Auth y potencialmente bloqueando cuentas legitimas.
    ALTO
  • D-04
    Dependencia de servicio unico (Supabase)
    Toda la autenticacion y persistencia depende de Supabase Cloud. Si Supabase experimenta una caida, el sistema completo queda inoperativo sin mecanismo de fallback o cache local.
    MEDIO
E  ELEVATION OF PRIVILEGE — Escalamiento de Privilegios
Amenazas de Escalamiento
Propiedad violada: Autorizacion — Un usuario obtiene permisos superiores a los asignados
  • E-01
    Auto-asignacion de rol admin via API
    Si el endpoint PUT /auth/users/{user_id}/role no valida correctamente que solo un admin puede invocar el cambio de rol, un usuario con rol de analista podria enviar una peticion directa al API para asignarse el rol de administrador.
    CRITICO
  • E-02
    Bypass de RBAC por manipulacion de frontend
    El control de acceso VIEW_ROLES se implementa en el frontend (App.jsx). Un atacante podria modificar el JavaScript en el navegador para saltarse las restricciones de vista y acceder a funcionalidades de administrador directamente.
    ALTO
  • E-03
    Registro con rol elevado por defecto
    El endpoint POST /auth/register-profile asigna el rol 'analista' por defecto. Si un atacante descubre como manipular el payload de registro para incluir un rol diferente (admin/auditor), podria obtener acceso privilegiado inmediato.
    ALTO
  • E-04
    Acceso cross-tenant via IDOR
    Un usuario podria manipular IDs en las URLs (Insecure Direct Object Reference) para acceder a recursos de otras empresas. Por ejemplo, cambiando el empresa_id en una peticion GET /empresas/{id} para ver datos de otra organizacion.
    CRITICO

Arboles de Amenazas

Representacion jerarquica de las rutas de ataque mas criticas identificadas en el sistema.

🌲 Arbol 1 — Comprometer datos de otra empresa
  • 🚨 OBJETIVO: Acceder a datos de otra organizacion (Cross-tenant breach)
    Impacto: Exposicion de incidentes, riesgos, controles y datos de auditoria de empresa ajena
    • E-04 IDOR en endpoint /empresas/{id}
      Cambiar el ID en la URL para acceder a datos de otra empresa
      • Enumerar IDs de empresa via requests secuenciales
        Si los IDs son enteros autoincrement, es trivial iterar 1, 2, 3...
    • T-04 Manipular empresa_id en payload de request
      Enviar un empresa_id diferente al asignado en POST/PUT
      • Backend no valida que empresa_id == user.empresa_id
        Si el filtro _empresa_filter() no se aplica al crear registros
    • I-01 Falla en filtro multi-tenant del dashboard
      /dashboard/summary retorna KPIs agregados sin filtrar por empresa
      • asyncio.gather() en dashboard_service agrega datos globales
        Las queries de incidentes, controles y riesgos no filtran por empresa_id
    • E-01 Escalar a rol admin y ver todos los datos
      Admin/auditor ven datos de todas las empresas por diseno
      • Auto-asignar rol admin via PUT /auth/users/{id}/role
      • Manipular payload de registro para obtener rol elevado
🌲 Arbol 2 — Falsificar metricas de cumplimiento
  • 📊 OBJETIVO: Falsificar KPIs de cumplimiento ISO para aparentar conformidad
    Impacto: Decisions erroneas de la direccion, aprobacion de auditorias falsas, incumplimiento real
    • T-01 Inflar compliance_pct de controles
      PUT /controls/{id} con compliance_pct=100 sin justificacion
      • No hay validacion de evidencia para cambios de cumplimiento
      • R-01 Sin audit trail del cambio
    • T-03 Reducir severidad de incidentes criticos
      Cambiar severity=critical a severity=low para mejorar estadisticas
    • Cerrar incidentes prematuramente sin resolucion real
      PUT /incidents/{id}/status con status=closed para mejorar resolution_rate
    • R-03 Manipular snapshots historicos
      POST /snapshots con datos fabricados para mostrar tendencia positiva
🌲 Arbol 3 — Obtener acceso administrativo completo
  • 👑 OBJETIVO: Obtener privilegios de administrador en el sistema
    Impacto: Control total sobre todas las empresas, usuarios, datos y configuracion
    • S-01 Robar JWT de un admin activo
      • XSS en campo de texto (title, description, notas)
        Inyectar script que envie el JWT al atacante
      • S-04 CSRF via CORS abierto
        Sitio malicioso hace requests al API con sesion de admin
    • E-01 Escalar privilegios directamente
      • PUT /auth/users/{self}/role con body {"role": "admin"}
        Si require_role no esta correctamente aplicado al endpoint
      • E-03 Manipular registro para obtener rol admin
        POST /auth/register-profile con {"role": "admin"} en el body
    • I-04 Obtener credenciales de infraestructura
      • Acceder al container Docker y leer variables de entorno
        DATABASE_URL + SUPABASE_SERVICE_ROLE_KEY = acceso total

Mitigaciones Propuestas

Contramedidas para cada categoria STRIDE, indicando estado actual (implementadas vs. pendientes).

🛡️ Mitigaciones — Spoofing
✅ Implementadas
  • JWT Stateless — Tokens validados via Supabase REST en cada request
  • Bearer Token — Inyeccion automatica via Axios interceptor
  • Password Hashing — Gestionado por Supabase Auth (bcrypt)
⚠️ Pendientes
  • Restringir CORS — Configurar allow_origins con dominios especificos en lugar de ["*"]
  • Token Refresh — Implementar rotacion de refresh tokens con TTL corto
  • MFA — Habilitar autenticacion multi-factor via Supabase
  • Verificacion de email — Confirmar dominio corporativo antes de activar cuenta
🛡️ Mitigaciones — Tampering
✅ Implementadas
  • SQLAlchemy ORM — Queries parametrizadas previenen SQL injection
  • Pydantic v2 — Validacion estricta de tipos en request/response
  • Multi-tenant filter — _empresa_filter() en routers filtra por empresa_id
⚠️ Pendientes
  • Validacion server-side de empresa_id — Verificar que empresa_id del payload coincida con el del usuario autenticado
  • Firma digital de snapshots — Hash de integridad para detectar manipulacion de datos historicos
  • Validacion de rangos — Restricciones de negocio para cambios de compliance_pct (no mas de +20% por actualizacion)
🛡️ Mitigaciones — Repudiation
✅ Implementadas
  • Timestamps automaticos — created_at/updated_at en todos los modelos
  • reported_by — Campo que registra quien reporto un incidente
⚠️ Pendientes
  • Audit Log completo — Tabla de auditoria que registre: quien, que, cuando, desde donde (IP)
  • Logging estructurado — Implementar logging con formato JSON para analisis SIEM
  • Historial de cambios — Versionado de registros criticos (controles, riesgos, incidentes)
🛡️ Mitigaciones — Information Disclosure
✅ Implementadas
  • RBAC — 4 roles con permisos diferenciados por vista y endpoint
  • Multi-tenant filtering — Datos filtrados por empresa_id segun rol
  • HTTPS — Comunicacion cifrada entre cliente y servidor
⚠️ Pendientes
  • Desactivar Swagger en produccion — Condicionar /docs y /redoc a DEBUG=true
  • Cifrado at-rest — Cifrar campos PII (NIT, email, telefono) en la base de datos
  • Secrets Manager — Migrar credenciales de .env a un vault (HashiCorp, AWS Secrets Manager)
  • Headers de seguridad — Agregar X-Content-Type-Options, X-Frame-Options, CSP, HSTS
🛡️ Mitigaciones — Denial of Service
✅ Implementadas
  • asyncpg Connection Pool — Pool de conexiones gestionado por SQLAlchemy async
  • Paginacion — Endpoints de listado limitan resultados con skip/limit
⚠️ Pendientes
  • Rate Limiting — Implementar slowapi o middleware custom (ej: 100 req/min por IP)
  • Login throttling — Bloquear IP tras 5 intentos fallidos en 5 minutos
  • Health monitoring — Alertas cuando Supabase o el backend no responden
  • Cache layer — Redis/memcached para endpoints de lectura frecuente (dashboard/summary)
🛡️ Mitigaciones — Elevation of Privilege
✅ Implementadas
  • require_role() — Dependency injection que valida roles en endpoints protegidos
  • Rol por defecto — Nuevos usuarios se registran como 'analista' (minimo privilegio)
  • RBAC backend — Autorizacion verificada en el servidor, no solo en frontend
⚠️ Pendientes
  • Ignorar role en registro — Endpoint register-profile debe ignorar cualquier campo 'role' del body
  • Ownership validation — Validar que el user_id del request corresponda al recurso accedido
  • Principio de minimo privilegio — Revisar todos los endpoints para asegurar que require_role sea lo mas restrictivo posible

Conclusiones y Recomendaciones

Hallazgos principales y hoja de ruta de seguridad basada en el analisis STRIDE.

El modelamiento de amenazas STRIDE aplicado al sistema ISO SECURE ha permitido identificar un total de 24 amenazas distribuidas en las 6 categorias del modelo. De estas, 8 fueron clasificadas como criticas y 13 como altas, lo que refleja areas de mejora significativas en la postura de seguridad del sistema.

Hallazgo principal: Las amenazas mas criticas se concentran en tres areas: (1) aislamiento multi-tenant — la separacion de datos entre organizaciones depende enteramente del helper _empresa_filter() en los routers, y cualquier omision expone datos entre empresas; (2) gestion de identidad y acceso — la configuracion CORS abierta y la ausencia de MFA amplian significativamente la superficie de ataque; y (3) trazabilidad — la falta de un audit trail completo imposibilita la investigacion forense y permite el repudio de acciones criticas.

Contramedidas existentes: El sistema ya implementa medidas positivas como autenticacion JWT via Supabase, RBAC con 4 roles diferenciados, validacion de datos con Pydantic v2, queries parametrizadas via SQLAlchemy (prevencion de SQL injection), filtrado multi-tenant en routers, cifrado en transito (HTTPS) y principio de minimo privilegio en el registro de usuarios.

Hoja de ruta de seguridad priorizada:

Prioridad 1 (Inmediata): Restringir CORS a dominios especificos, implementar rate limiting, validar empresa_id server-side en todos los endpoints de escritura, e ignorar el campo 'role' en el registro de usuarios.

Prioridad 2 (Corto plazo): Implementar audit log completo, desactivar Swagger en produccion, agregar headers de seguridad HTTP, y configurar login throttling.

Prioridad 3 (Mediano plazo): Habilitar MFA, cifrar PII at-rest, migrar secretos a un vault, implementar versionado de registros criticos, y agregar monitoreo y alertas de seguridad.
